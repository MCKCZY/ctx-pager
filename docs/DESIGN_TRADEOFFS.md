# 设计权衡与局限性说明

构建 `ctx-pager` 时，每个关键决策都面向同一个约束：**零外部依赖、可作为轻量 Skill 随项目携带、并在 4K–16K 小窗口上可控运行**。以下是核心取舍与明确的非目标边界。

## 1. 六项核心工程权衡

### 1.1 SQLite + FTS5 + 稀疏 TF-IDF vs. 外部向量数据库 (Qdrant / Chroma / Milvus)
- **选择**: 默认完全内置于 Python 标准库 + SQLite WAL/FTS5，同时抽象 `Embedder` Protocol 保留扩展槽位。
- **代价**: 纯局部词汇与字符 n-gram 在零词面重叠的同义跨语言场景（例如库里只写了 `"OOM"` 而用户只搜 `"内存溢出"` 且未建图边）召回能力弱于稠密向量模型。
- **依据**: 作为可随仓库分发的 Agent Skill，如果要求用户在面试演示或本地小模型环境先拉起 Docker、向量库和 Embedding 推理服务，使用门槛会急剧上升。对于代码仓库、错误码、文件路径、配置项等工程场景，BM25 + 精确标识符抽取 + 稀疏 subword 在 10–15ms 内即可稳定命中且无幻觉近邻。

### 1.2 多分辨率 `L0/L1/L2` 调页 vs. 平面 Top-K 切片
- **选择**: 优先让更多相关记忆以 `L0/L1` 摘要入场，再按 `score * delta_U / delta_tokens` 升级高价值条目至 `L2`，并在尾部附带 `page_in_hints`。
- **代价**: 在极小预算（如 1024 tokens）下，部分极长堆栈不会在首轮直接全文展开，需要智能体发起一次 `page-in <ID>` 工具调用（对应基准测试中 1024 budget 下 92.6% Direct Recall 与 100.0% Effective Recall 的差距）。
- **依据**: 平面 Top-K 按全长切片填充时，3–5 条冗长记录就会吃光 1024 tokens，导致其余约束和关键线索直接被截断不可见。保留 `L0` 指针相当于为小上下文智能体提供了按需访存的目录页。

### 1.3 显式 `supersede` 状态机 vs. 依赖时间戳让模型自行裁决
- **选择**: 通过 `supersede` 显式将旧记录标记为 `superseded`，默认启用冲突门控在检索层过滤失效记录。
- **代价**: 要求智能体或摄取流程在方案变更时执行 `supersede`（而非再次 `commit` 一条矛盾记录）。
- **依据**: 在长程对话中把“端口 8080”和“端口 9443”同时塞进提示词让小参数模型（如 7B/8B）靠时间戳自己分辨，极易产生旧值回响（Stale Decision Echo）。基准测试证明，关闭冲突门控时 `flat_bm25` 和 `ctx_pager_ablated` 的过时信息入侵率均达到 100.0%，开启后降至 0.0%。

### 1.4 CJK 二元组 + 过滤单字 + 代码正则 vs. 引入 `jieba` 分词
- **选择**: 仅使用标准库正则实现 CJK bigram + 非停用词 unigram 与代码边界切分。
- **代价**: 对纯文学或极泛化的中文长句而言，bigram 索引体积略大于词典分词，且无法识别未登录词的词性。
- **依据**: 技术对话中的关键信息往往是中英混杂的实体（如 `MySQL 5.7 索引不超过 191`、`Redis 锁超时`）。保留代码完整标识符（通过 FTS5 `tokenchars '_'`）并配合 CJK bigram/unigram 既消除了第三方依赖，又避免了词典分词把技术词切碎。

### 1.5 Append-Only 哈希链账本 vs. 原地覆写更新
- **选择**: 所有写操作均追加到哈希链保护的 `events` 表，再同步投影到 `memories` 物化视图。
- **代价**: 长期运行会产生额外约 1.5x–2x 的事件日志存储开销，且写入路径多一次 JSON 序列化与 SHA-256 计算。
- **依据**: 内存压缩（Compaction）与决策覆写如果只做原地修改，一旦压缩出错或出现误覆写，开发者无法排查问题发生的准确轮次。哈希链账本提供了零成本的 `replay --turn N` 时间回放与 `doctor` 完整性审计。

### 1.6 上下文 Skill 的“自举悖论”控制
- **选择**: 将 `skills/ctx-pager/SKILL.md` 严格压缩至 82 行（约 1,136 个估算 tokens），把细则拆分到 `references/` 按需加载。
- **依据**: 一个旨在节省上下文窗口的 Skill 如果自身说明文档就占掉 3,000+ tokens，会直接违背设计初衷。

## 2. 与常见方案的客观对比

| 维度 | Sliding Window | Rolling Summary | Mem0 / 常规 RAG | MemGPT / Letta | `ctx-pager` |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 运行依赖 | 无 | LLM 总结调用 | 向量库 + LLM + Embedder | 常驻服务 + LLM | Python 3.10+ 标准库 (SQLite FTS5) |
| 严守硬预算不变量 | 是 | 近似 | 取决于切片长度 | 需系统协调 | 是 (`used <= budget` 渲染后强制校验) |
| 多分辨率信息分级 | 无 | 单一摘要 | 单一切片 | Core/Recall 二分 | `L0` 指针 / `L1` 摘要 / `L2` 详文 + 按需 `page-in` |
| 过时决策冲突抑制 | 无 | 易混淆旧摘要 | 需 LLM 后验去重 | 依赖模型主动编辑 | 原生 `supersede` 状态机与检索层门控 |

## 3. 明确的非目标与已知局限 (Non-Goals & Limitations)

1. **非全自动强语义理解器**:
   内置的离线 `TurnIngestor` 基于双语规则提取，适合作为兜底或流水线预处理，语义概括能力远不如智能体在工作流中主动调用 `commit` / `supersede`。对于高度隐晦的口语隐喻，仍依赖调用方智能体遵循 Skill 规程显式落盘。
2. **无词面重叠且未建图的纯同义召回**:
   在默认零依赖模式下，若用户查询使用的词汇与历史记录既无词根/子词重合、又无共享实体及图关联边，纯稀疏检索可能漏召回；此时需通过实现 `vectorizer.Embedder` 协议接入外部稠密向量模型。
3. **非分布式高并发存储**:
   底层采用单机 SQLite WAL 模式，适合单智能体或少量本地工作进程串行/低并发读写，不适用于数十个分布式 Worker 同时高频写入同一个记忆库。
4. **保守的 Token 估算偏差**:
   `estimate_tokens()` 是面向跨模型安全设计的确定性启发式估算器，会比特定模型的精确 BPE 分词器（如 `tiktoken` 或 Qwen 分词器）略微高估约 5%–10%，以此换取绝不触发上下文越界报错的确定性。
